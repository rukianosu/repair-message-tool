## 0. 設計原則：属人性の排除（全実装の最上位指針）

**人は辞める・忘れる・怒る・慌てる・動揺する・疲れる。それでも壊れない仕組みを作る。**

- 人が担うのは「判断」だけ：新規/既存の判断、管理番号の採番、台（枝番）の振り分け、返信内容の確定。
- 作業と抜けの検知はすべて仕組み：集約、画像添付、状態遷移、放置検知、**そしてブリッジ自身の生存確認も**。
- 判断基準は「めんどくさいかどうか」。人が毎回めんどくさいと感じる作業は必ず抜ける。全部自動化する。
- 状態（🔴🟢）は人が触らない。システム専管。
- **システム自身の故障も「機械が検知する」**（第9章）。人が「動いてるかな」と見に行った時点で属人性。
- この仕組みは人を監視するためでなく、人を消耗から守るためにある。

## 1. 目的とスコープ

**目的**：Lステップを使わず、LINE Messaging APIを直接使い、顧客対応をAsanaに一元集約。Asanaを案件管理の唯一の正にする。

**やること（MVP）**：受信集約／画像・動画・ファイル添付／3状態自動遷移／受付自動返信（replyToken）／Asana→LINE返信／重複排除／ループ防止／生存監視。

**やらないこと**：マーケ配信／メール連携（将来、同構造で横展開）／Unitsとの自動連携（人が参照）／グループトーク対応（**1対1トークのみ**を対象とする）。

**Phase 2（MVP後、すぐ着手可能）**：AI返信案＝参謀連携（第11章）。

## 2. 全体構成

```
お客様 ─ LINE ─→ LINE公式アカウント
                     │ Webhook（HTTPS・署名検証・重複排除）
              ┌──────────────────────────┐
              │ ブリッジ（Node.js + TypeScript）      │
              │  ├ 紐付けDB（SQLite→将来Supabase）    │
              │  ├ Asana API（作成/コメント/状態/添付）│
              │  ├ LINE API（reply/push/コンテンツ取得）│
              │  └ 生存記録（最終受信・最終送信時刻）   │
              └──────────────────────────┘
                     │
              Asana（PC修理プロジェクト＝唯一の正）
                     ↑
              参謀（Claude Code）＝棚卸し・返信案・状況要約に利用
```

- 言語：Node.js + TypeScript／Express（Honoでも可）
- DB：SQLite（better-sqlite3）→将来Supabase
- ホスティング：クラウド（Render/Cloud Run、東京リージョン、ISMS配慮）
- 常時起動・HTTPS必須

## 3. データの持ち方

```
Units（顧客マスター・LANのツール）… 人が目で参照。新規/既存の判断もここ
        ↓ 人が管理番号を決める
Asana（案件管理の正）
  タスク ＝ お客様1人（＝1つのLINEユーザー、親番号 例:1141）
  サブタスク ＝ 台ごとの案件（枝番 1141-1, 1141-2…）
```

- **LINE 1人＝親タスク1本を1対1紐付け**。会話・添付はすべて親タスクに時系列集約。
- どの台（枝番）の話かの振り分けは人。台ごとの機種・症状・見積・状態はサブタスクで人が管理。
- 再入庫（同じ機体が戻ってくる）：シリアルナンバーで同一機を人が照合し、同じ枝番を復活させる。**照合は人の判断、手順は共通ルール化**（別途「再入庫ルール」参照。細部TBD）。

### 紐付けのライフサイクル（v3で明確化）
- 案件がすべて完了しても、**mapping（LINE⇔親タスク）は削除しない**。
- 同じお客様から再びLINEが来たら、既存の親タスクに集約し、🔴未返信に戻す（休眠からの復活）。
- 親タスク自体をAsanaで完了にしていた場合：ブリッジはコメント追記＋「完了済みタスクに新着あり」を棚卸しレポートで検知対象にする（勝手に再オープンしない＝変更は人の判断）。

## 4. 【要検証】紐付けキー（実装の最初のタスク）

`profile.displayName` で何が取れるかをテストメッセージ1通で実機確認。

| 結果 | 方式 |
|---|---|
| 管理番号入りの表示名が取れる | A: 表示名から番号を抽出して主キー |
| 取れない（通常こちら） | B: 初回受信で「未割当タスク」自動作成→人がタスク名を `1141 田中太郎` に書き換え→システムが読んでDB登録 |

**未割当タスクの放置防止（v3追加）**：未割当のまま**営業時間内3時間**超えたら棚卸し/レポートの最優先に出す。新規のお客様を最初に待たせるのが一番まずい。

## 5. 受信処理（メッセージ種別の網羅・v3拡充）

| 種別 | 処理 |
|---|---|
| text | 親タスクにコメント「📩 お客様: 本文」 |
| image | コンテンツ取得→タスクに添付＋コメント「📷 画像を受信」 |
| **video** | 取得→添付（サイズ上限超は「動画を受信(サイズ大・LINE管理画面で確認)」とコメント） |
| **audio** | 同上「🎤 音声を受信」 |
| **file** | 取得→添付＋ファイル名をコメント |
| **sticker** | コメント「(スタンプ)」のみ。添付不要 |
| location | コメントに住所/座標を書く（出張見積に有用） |
| その他 | 「(未対応種別: type)」とコメント。**無視して落とさない** |

### フォロー/ブロックイベント（v3追加）
- **follow（友だち追加）**：未割当タスク作成の起点。コメント「新規友だち追加」
- **unfollow（ブロック）**：mappingに記録し、親タスクにコメント「⚠️ お客様がブロック（送信不可）」。以後この宛先へのpushは行わない。棚卸しの検知対象。

### 重複排除（v3追加・必須）
- LINEは応答遅延時にWebhookを**再送**する。`message.id`（またはwebhook event id）をDBに記録し、**既知IDは黙ってスキップ**。同じ発言がAsanaに2回載るのを防ぐ。
- 受信したら即200を返し、重い処理は後続で行う（再送自体を減らす）。

## 6. 状態管理（3状態）と既存Asana構造との整合（v3で解決）

### 3状態
| 状態 | 契機 | 操作者 |
|---|---|---|
| 🔴 未返信 | LINE受信時（前回🟢でも強制で戻す） | システム |
| 🟡 対応中 | 着手 | 人 |
| 🟢 返信済み | LINE送信成功時 | システム |

🔴🟢は人が触らない。放置の検知は棚卸しが担う。

### 既存セクションとの共存（棚卸しで判明した実態を反映）
現在のAsanaには「音信不通」「＊要連絡、要注意」「完了(Completed)」等の**運用中セクションが既にある**。3状態をセクションで持つと既存運用と衝突するため、**v3の決定：LINE3状態はセクションではなくカスタムフィールドで持つ**。

- CF「LINE状態」（ドロップダウン：未返信/対応中/返信済み）を新設し、ブリッジはこれを更新する。
- セクション（音信不通・要連絡等）は従来通り人の運用に残す。ブリッジは触らない。
- ボードで見たい場合は「LINE状態」でフィルタ/ソートすれば足りる。
- 既存CF「状態」（入金待ち等）とは別物として共存。棚卸しは両方を判定材料にする。
- ※既にCF「担当者」とAssigneeの二重管理が発覚している。**担当はAssigneeに一本化**（CF「担当者」は廃止方向）。同じ轍を踏まないため、LINE状態のCFは1つだけ作り、責任範囲（ブリッジ専用）を明記する。

## 7. 受付自動返信（v3でコスト設計を修正）

- **受信直後の自動返信は replyToken を使う（無料・通数を消費しない）**。push（通数課金対象）は使わない。
- 文面（営業時間内）：「メッセージを受け付けました。担当者より順次ご連絡いたします。（受付時間 9:00〜18:00、日曜・祝日定休）」
- **営業時間外・定休日は文面を変える**：「営業時間外のため、翌営業日に順次ご連絡いたします。（受付時間 9:00〜18:00、日曜・祝日定休）」
- 連投抑制：直近30分に自動返信済みならスキップ（DBの auto_reply_at で判定）。
- スタッフ返信（Asana経由・時間差あり）は push を使う（これは通数対象。月間通数の監視は棚卸しレポートに件数を出す）。

## 8. Asana → LINE返信

- MVP：親タスクのコメントに `>>返信 本文` と書く → ブリッジが検知 → LINE push送信。
- 検知：Asana Webhook（story追加）またはポーリング。実装が楽な方から。

### ループ防止（v3追加・必須）
- **ブリッジ自身が書いたコメントには反応しない**。判定方法：ブリッジ用Asanaアカウント（またはPAT所有者）のuser gidを起動時に取得し、story作成者が自分なら無視する。加えてブリッジのコメントには先頭に識別子（例「📩」「✅」）を付け、`>>返信` 判定の対象外とする。

### 送信成功時
- CF「LINE状態」を🟢返信済みに／「最終返信日時」更新
- 元コメントに ✅ リアクションまたは「✅ 送信済み HH:MM」を追記

### 送信失敗時（v3追加・必須）
- **🟢にしない。🔴のまま維持。**
- 失敗理由をコメントで書き戻す：「❌ 送信失敗: （ブロックされている/トークン失効/レート制限 等）」
- 失敗は棚卸しレポートの最優先項目。**「返したつもりで返っていない」を構造的に消す。**

## 9. ブリッジの生存監視（v3追加・最重要の網）

**サーバが死ぬと受信が無音で消える。これを機械が検知する。**

- ブリッジは「最終Webhook受信時刻」「最終送信時刻」「起動時刻」をDBに記録し、`GET /health` で返す。
- **毎朝の棚卸しに組み込む**：棚卸し実行時に /health を叩き、レポート冒頭に必ず1行出す。
  - 「ブリッジ稼働: 正常（最終受信 7/14 18:22）」
  - 応答なし → 「🚨 ブリッジ応答なし。LINE受信が失われている可能性。最優先で確認」
- 判定目安：/health 応答なし＝最優先。営業日に24時間以上受信ゼロ＝要確認（受信ゼロ自体は正常もありうるが、一言レポート）。
- これにより「システムの故障を人が偶然見つける」を排除する。

## 10. データモデル（SQLite・v3拡充）

```sql
CREATE TABLE IF NOT EXISTS mappings (
  key              TEXT PRIMARY KEY,   -- 管理番号（親番号）
  line_user_id     TEXT NOT NULL,
  asana_task_gid   TEXT NOT NULL,
  customer_name    TEXT,
  blocked          INTEGER DEFAULT 0,  -- unfollow検知
  last_received_at TEXT,
  last_replied_at  TEXT,
  auto_reply_at    TEXT
);
CREATE INDEX IF NOT EXISTS idx_line_user ON mappings(line_user_id);

CREATE TABLE IF NOT EXISTS processed_events (   -- 重複排除
  event_id     TEXT PRIMARY KEY,               -- LINE message.id / event id
  processed_at TEXT
);

CREATE TABLE IF NOT EXISTS health (             -- 生存監視
  k TEXT PRIMARY KEY,                           -- 'last_webhook_at' 等
  v TEXT
);
```

## 11. 参謀連携（Phase 2 だが設計は今固める）

**会話がAsanaに集約された時点で、参謀はLINE対応の文脈を全部読める。** 参謀はAsana APIに既にアクセスできる（棚卸しで実証済み）。追加開発はほぼ不要で、次が可能になる：

- **状況要約**：「6847 森様のコメント履歴を読んで状況を3行で」
- **返信案の生成**：「このタスクの会話を読んで、返信案を3つ。ルキテックのトーン（高ブランド・値引きしない・丁寧）で」
- **人が確定**：橘さん/ロレインが案を選び手直しして `>>返信` に貼る → ブリッジが送信
- **判断は人・作業は仕組み** の原則通り：参謀は案を作るまで。送信の確定は必ず人。

将来（Phase 3）：ブリッジが新着受信時に自動で参謀APIを呼び、返信案をあらかじめタスクにコメントしておく（人は選ぶだけ）ことも可能。ただしMVP完了後に判断。

## 12. セキュリティ（ISMS事業者として必須）

- LINE署名検証（`x-line-signature`）。失敗は401。
- トークン類は環境変数のみ。リポジトリに書かない。`.gitignore` 必須。
- Webhookに rate limit。
- 会話ログ・添付の保管リージョン（東京）・暗号化・保持期間を社内規程に明文化。
- ログに個人情報を平文で残しすぎない。検証用アカウントで開発し、本番顧客データで実験しない。

## 15. 完了の定義（MVP）

- [ ] LINE受信がAsanaコメントに残る（重複しない）
